# 작업 흐름

[English](../en/workflow.md)

Heirloom은 개발 작업을 대신하지 않습니다. Superpowers 같은 SDLC 도구로 끝낸 작업을 넘겨받아, 사람이 승인한 PR 요약과 결정(decision)·규칙(axiom)을 저장소에 남깁니다.

```
1. 인계 준비  →  2. 대시보드 승인  →  3. 반영과 PR  →  4. 다음 작업에서 맥락 조회
   (에이전트)        (사람)              (에이전트)         (에이전트)
```

## 1. 인계 준비

에이전트가 맡습니다.

- **언제 하나요.** spec 기반 작업의 구현과 최종 리뷰를 마친 뒤, 완료를 보고하기 전에 `prepare-handoff` 스킬을 실행합니다.
- **놓쳤을 때.** 종료 훅이 한 번 상기시킵니다. 조건은 세 가지입니다: spec에 연결된 코드 변경이 있고, 그 상태로 인계한 적이 없고, 같은 상태로 상기한 적이 없을 때입니다.
- **spec이 없는 작업.** 작은 수정 같은 작업은 사용자가 요청할 때만 인계합니다.
- **준비 과정.**
  1. 현재 소스 상태와 자료(spec, 리뷰 문서)를 고정합니다.
  2. 에이전트가 PR 요약과 decision·axiom 초안을 씁니다.
  3. Heirloom이 초안의 출처 인용을 기계적으로 검사합니다. 인용이 원문에 없으면 초안을 올리지 않습니다.
- **결과.** 검사를 통과하면 작업마다 처음 한 번 대시보드가 열립니다. 사람이 읽을 인계 파일(`handoff.md`)도 만들어집니다.

인계는 "작업이 준비됐다"는 에이전트의 보고일 뿐, 작업이 맞다는 증거나 승인이 아닙니다.

## 2. 대시보드 승인

사람이 합니다. 자세한 화면 설명은 [대시보드](dashboard.md)에 있습니다.

1. PR 요약을 확인하고 필요하면 고칩니다.
2. decision 항목마다 승인·거절·보류를 고릅니다.
3. axiom 항목은 이후 모든 작업에 적용되므로 하나씩 따로 고릅니다.
4. "승인 저장"을 누릅니다. 승인 기록은 사용자 서명 키로 서명되어 저장됩니다.

decision·axiom 변경이 없는 작업은 요약만 확인하는 **간이 승인**으로 끝납니다. 화면을 열거나 닫은 것만으로는 승인으로 보지 않습니다.

승인은 몇 시간 뒤에 해도 됩니다. 에이전트는 승인을 기다리느라 세션을 붙잡아 두지 않습니다. Claude Code에서는 인계 뒤 최대 60분 동안 백그라운드로 승인을 기다립니다. 세션이 열려 있는 동안 승인하면 묻지 않고 바로 반영합니다(3절). 그렇지 않으면 세션을 끝낼 수 있고, 다음 세션이 승인을 이어받습니다.

## 3. 반영과 PR

에이전트가 맡습니다.

인계한 세션이 아직 승인을 기다리고 있으면, 승인하는 즉시 이 단계를 시작합니다. 그렇지 않으면 에이전트에게 "승인된 인계 반영해줘"라고 요청하면 `apply-approval` 스킬이 다음 순서로 진행합니다. 다음 세션을 시작할 때 미처리 승인이 있으면 에이전트가 먼저 알려 주고 요청을 기다립니다.

1. **승인 확인.** 서명을 검증하고, 승인한 초안과 현재 초안이 같은지 확인합니다. 하나라도 다르면 미승인으로 취급합니다.
2. **상태 대조.** 승인한 브랜치와 소스 상태가 그대로인지 확인합니다. 승인 뒤 코드가 바뀌었으면 반영하지 않고 다시 인계해야 합니다.
3. **기록 쓰기.** `.heirloom/decisions/`, `.heirloom/axioms/`에 기록 파일을 씁니다. 대체·폐기된 기록은 지우지 않고 비활성으로 표시합니다.
4. **커밋과 PR.** 기록 파일을 커밋하고, 승인된 요약을 고치지 않고 그대로 넣어 `gh`로 PR을 만듭니다. 요약은 프로젝트 PR 템플릿의 요약 섹션에 들어가고, 템플릿이 없으면 본문 맨 위에 들어갑니다.
5. **이미 PR이 있을 때.** 같은 브랜치에 PR이 있으면 새로 만들지 않습니다.

같은 승인을 여러 번 반영해도 기록은 한 번만 쓰입니다.

PR을 만들 수 없으면(원격이 github.com이 아니거나, `gh`가 없거나 로그인되지 않음) 기록 파일을 쓰고 커밋한 뒤 멈춥니다. PR은 직접 만들거나 브랜치를 직접 머지합니다. 승인된 기록이 대상 브랜치에 들어가면 작업은 끝난 것으로 봅니다. 세션 시작 목록에서 빠지고, 대시보드에는 '머지됨'으로 보입니다.

PR이 머지되지 않고 닫히면 작업은 만료되고, 그 기록은 활성이 되지 않습니다. 에이전트가 그 작업을 다시 반영하려 할 때나 대시보드 전체 목록을 볼 때 `gh`로 확인합니다. `gh`가 없거나 오프라인이면 대기 상태를 유지합니다.

## 4. 다음 작업에서 맥락 조회

에이전트가 맡습니다.

- **세션 시작.** 활성 axiom 요약과 활성 decision 색인이 에이전트에게 주입됩니다. 현재 변경과 관련된 decision이 위에 옵니다.
- **작업이 정해진 뒤.** 에이전트가 `recall-context` 스킬로, 작업할 파일·주제·기록 ID와 관련된 기록의 원문을 가져옵니다. 결과마다 왜 골랐는지가 함께 나옵니다. 경로가 겹친다는 것은 단서일 뿐이므로 에이전트는 기록의 적용 범위를 직접 읽고 판단합니다.
- **상한.** 한 번에 최대 `recall.maxRecords`개, `recall.maxTokens` 토큰까지 가져옵니다([설정](configuration.md#프로젝트-설정)). 상한 때문에 빠진 기록은 ID로 알려 주므로 에이전트가 따로 요청할 수 있습니다.

### 기록이 활성이 되는 때

| 상태 | 뜻 | 규칙으로 제공 |
| --- | --- | --- |
| 활성 | 기록 파일이 대상 브랜치에 머지됨 | 예 |
| 머지 대기 | 승인되어 작업 브랜치에 쓰였지만 아직 머지되지 않음 | 승인한 작업에만 제공합니다. 다른 작업에는 ID와 제목만 경고로 보입니다. |
| 비활성 | 대체·폐기가 머지됨 | 아니요. 이력으로 남습니다. |
| 미확인 | 대상 브랜치를 정할 수 없음 | 작업 트리의 기록을 쓰고 '미확인'으로 표시합니다. |

- **fetch하지 않음.** 세션 시작과 맥락 조회는 로컬의 원격 추적 브랜치(예: `origin/main`)와 비교하고 fetch하지 않습니다. 마지막 fetch 시각을 함께 알려 주므로, 그 뒤의 머지는 다음 fetch 전까지 보이지 않습니다. 승인을 반영할 때는 대상 브랜치를 fetch합니다.
- **병렬 작업.** 같은 저장소의 다른 작업 트리에서 승인한 대체·폐기는 머지되기 전까지 경고로 보입니다.
- **PR 리뷰 중 수정.** 머지된 문구가 기준입니다.
