# 보안 모델과 한계

[English](../en/security.md)

개발 에이전트는 셸과 파일 쓰기 권한을 가집니다. 그래서 Heirloom은 에이전트의 승인 위조를 완전히 막는 것이 아니라, **탐지하고 감사할 수 있게 하는 것**을 목표로 합니다.

## 승인 서명

- 대시보드는 승인 기록에 사용자별 ed25519 키로 서명합니다.
- 서명 대상에는 승인한 소스 상태, 자료 해시, 초안 다이제스트, 최종 요약, 항목별 결정, 승인 시각, 승인자(공개키 지문과 git 사용자)가 들어갑니다.
- 기록을 쓰고 PR을 만들기 전에 서명을 검증합니다. 다음 경우는 미승인으로 취급하고 아무것도 쓰지 않습니다.
  - 서명이 없거나 맞지 않을 때
  - 승인 뒤에 초안이 바뀌었을 때
- 개인키는 다음 순서로 보관합니다.
  1. macOS 키체인
  2. Linux `secret-tool`(D-Bus 세션이 있을 때)
  3. 둘 다 안 되면 `~/.heirloom/keys/private.key`(권한 0600)
- 키를 교체해도 이전 공개키는 `keys/public/`에 남겨, 과거 승인을 계속 검증할 수 있습니다.

## 대시보드 서버

- `127.0.0.1`에만 바인딩합니다. 다른 컴퓨터에서는 접속할 수 없습니다.
- `Host`와 `Origin`이 대시보드 주소가 아니면 거부합니다. CORS를 허용하지 않고, 사이트 간 요청(`Sec-Fetch-Site: cross-site`)도 거부합니다.
- 상태를 바꾸는 요청(승인, 폐기)에는 서버가 시작할 때 메모리에서 만든 세션 토큰이 필요합니다. 토큰은 디스크에 저장하지 않습니다.
- 화면은 엄격한 콘텐츠 보안 정책(CSP)으로 인라인 스크립트를 막습니다.

## 헤드리스 정리 실행

Heirloom이 에이전트를 직접 실행하는 경우는 [맥락 정리](curation.md)뿐이며, 사용자가 대시보드에서 고를 때만 실행합니다.

- 실행 명령은 사용자 설정 `curation.agent`에서 읽습니다. 대시보드 요청으로는 고르거나 바꿀 수 없습니다. 실행 요청의 본문은 비어 있어야 하고, 승인처럼 세션 토큰이 필요합니다.
- 프롬프트는 작업 ID, worktree 경로, 따를 스킬만 담은 고정 문장입니다. 요청 내용이나 기록 본문을 명령줄에 넣지 않습니다.
- 에이전트는 전용 worktree에서, 단계마다 제한된 도구만 쓰고 실행됩니다. 초안 단계: 읽기 도구, 자신의 `draft.json` 쓰기, 정리·제출 스크립트. 반영 단계: 읽기 도구, PR 본문 파일 쓰기, 반영 스크립트, `git add .heirloom*`, `git commit`, `git push`, `gh pr create`, `gh pr edit`, `glab mr create`, `glab mr update`.
- 사용자 권한과 사용자의 `gh`·`glab` 로그인으로 실행됩니다. 대시보드 세션 토큰을 얻을 수 있는 프로그램은 정리도 시작할 수 있습니다. 아래 승인 한계와 같은 수준입니다.

## 알려진 한계

같은 OS 사용자 권한으로 실행되는 프로그램, 즉 개발 에이전트 자신은 다음을 막지 못합니다.

- **키 파일 읽기.** 개인키가 파일로 보관된 경우, 같은 사용자 권한으로 키를 읽어 승인을 위조할 수 있습니다. 키체인을 쓰면 위험이 줄지만 없어지지는 않습니다.
- **대시보드 경유 승인.** 같은 사용자 권한의 프로그램은 대시보드 페이지를 받아 세션 토큰을 얻고 승인 API를 호출할 수 있습니다.

이 한계는 의도적인 우회에 대한 것입니다. 탐지를 위해 다음을 남깁니다.

- 대시보드 서버는 승인 요청마다 `User-Agent`와 `Sec-Fetch-*` 헤더를 `~/.heirloom/server/server.log`에 기록합니다. 브라우저가 아닌 프로그램이 보낸 요청을 가려내는 데 도움이 되지만, 헤더는 위조할 수 있으므로 증거로는 충분하지 않습니다.
- 승인 기록과 저장소의 기록 파일에는 승인 키 지문이 남습니다. PR 리뷰 때 `.heirloom/` 변경을 함께 확인하세요.

## 권장 사항

- 키체인을 쓸 수 있는 환경이면 키체인을 쓰세요(기본 동작).
- 에이전트에게 `~/.heirloom/`를 직접 읽거나 쓰게 하는 지시를 주지 마세요.
- 승인하지 않았는데 승인된 것처럼 보고하는 경우가 있으면 `server.log`와 승인 기록의 시각을 확인하세요.
