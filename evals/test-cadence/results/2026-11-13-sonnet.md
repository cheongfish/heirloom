| fixture | `~/heirloom-acceptance/cadence-off`, `~/heirloom-acceptance/cadence-phase` |

## 계획

| | off (기준선) | phase |
| --- | --- | --- |
| 구조 | Task 2개, phase 없음 | Phase 1(변환: Task 1·2) → Phase 1 gate, Phase 2(표시: Task 3) → Phase 2 gate (최종) |
| task의 테스트 단계 | 대상 테스트(실패 확인) → **전체 테스트**(`node --test`) | 대상 테스트(실패 확인) → 대상 테스트(통과 확인) |
| 전체 테스트 위치 | task마다 | phase 관문마다 |

## 구현 중 테스트 실행 (`count-test-runs.mjs`)

| | off | phase |
| --- | --- | --- |
| 전체 테스트 | 4 (task 구현자 2, 메인 1, 최종 리뷰어 1) | 3 (Phase 1 gate 1, Phase 2 gate 1, 최종 리뷰어 1) |
| task 단위의 전체 테스트 | 2 / task 2개 | **0** / task 3개 |
| 대상 테스트 | 2 | 16 |
| 하위 에이전트 | 5 | 7 |
| 최종 전체 테스트 | 11 통과 | 16 통과 |

- phase의 구현자 지시문 3개 모두에 메인 에이전트가 규칙을 옮겨 적었다. 예: "Test cadence (user's rule): run ONLY the focused command the plan gives … Do NOT run the full suite; a phase gate does that, not the task." 리뷰어 지시문에도 "no full suite"가 들어갔다.
- 최종 리뷰어 지시문에는 "The full suite already passed at the last gate; you may re-run it"이 들어갔고, 리뷰어는 한 번 다시 돌렸다.
- 두 세션 모두 마지막에 Heirloom 인계(`awaiting_approval`)까지 갔다. 인계 전 마지막 전체 테스트는 phase에서 Phase 2 gate다.

## 해석

- 의도대로 동작했다. task 단위의 전체 테스트가 사라지고 phase 관문으로 옮겨갔으며, 규칙이 하위 에이전트까지 전달됐다. Superpowers TDD 스킬의 "task 범위와 무관하게 전체 테스트" 규칙보다 설정 규칙이 우선했다.
- 대신 대상 테스트 실행이 늘었다(2 → 16). 대상 테스트는 전체보다 짧으므로 테스트가 오래 걸리는 프로젝트일수록 이득이 크다. 이 fixture는 테스트가 수 밀리초라 벽시계 시간 차이는 측정할 수 없었다(두 세션 모두 약 3~4분, 대부분 모델 시간).
- 두 계획의 task 수가 달라(2개, 3개) 비용과 시간을 직접 비교하지 않았다. 효과는 task 수가 많을수록 커진다: off는 task 수만큼, phase는 phase 수 + 최종 리뷰만큼 전체 테스트를 돈다.

## 남은 확인

- 테스트가 느린 실제 프로젝트에서 시간 절감을 잰다.
- 같은 조건을 여러 번 돌려 편차를 본다(이번은 각 1회).

## 추가 실행: 리뷰어 규칙과 관문 규칙 (phase만)

1차 뒤에 규칙을 두 번 보강하고 phase fixture를 새로 만들어 다시 돌렸다.

| | 1차 | 2차 | 3차 |
| --- | --- | --- | --- |
| 추가한 규칙 | — | 리뷰어는 보고된 실행을 근거로, 의문이 있을 때만 대상 테스트 | 관문은 task가 아니며 메인 에이전트가 다음 phase 전에 직접 돌리고 건너뛰지 않음 |
| 허용 도구 | `Bash(cd *)` 없음 | `Bash(cd *)` 없음 | `Bash(cd *)` 추가 |
| fixture | `cadence-phase` | `cadence-phase2` | `cadence-phase3` |
| task 단위 전체 테스트 | 0 | 0 | 0 |
| phase 관문 전체 테스트 | 2 (Phase 1, 2) | **1 (Phase 1 생략)** | **2 (Phase 1, 2)** |
| 리뷰어 테스트 실행 | 대상 3 | 0 | 0 |
| 최종 리뷰어 전체 테스트 | 1 | 0 | 0 |
| 구현자 대상 테스트 | 13 | 1 (권한 거부 뒤 메인이 대신 실행 3) | 8 |
| 최종 결과 | 16 통과, 인계 | 11 통과, 인계 | 10 통과, 인계 |
| 비용 | $1.32 | $1.11 | $1.46 |

- 2차: Task 1 구현자의 `cd … && node --test …`가 "Permission to use Bash has been denied"로 거부됐다. 그 뒤 메인 에이전트는 구현자에게 Bash 없이 파일만 고치게 하고 대상 테스트를 직접 돌렸다. 이 과정에서 Phase 1 관문을 건너뛰고 Task 3 커밋 때 전체 테스트를 한 번만 돌렸다. 관문을 누가, 언제 돌리는지 규칙에 없던 것이 원인이라 3차 전에 관문 규칙을 보강했다.
- 3차: Phase 1 관문(09:27:15)은 Task 2 리뷰 뒤, Task 3 구현 전에 메인 에이전트가 돌렸다. Phase 2 관문(09:27:56)은 마지막 task 뒤, 인계 전에 돌렸다. 리뷰어 넷(task 리뷰 셋, 최종 리뷰 하나)은 테스트를 다시 돌리지 않았다. Task 1 구현자의 명령 하나(`cd …; mkdir …` 뒤 heredoc)가 여전히 권한 거부됐지만, 구현자는 다른 방법으로 이어 갔고 대상 테스트를 정상 실행했다.
- 결론: 규칙이 의도대로 동작했다. task 단위 전체 테스트 0, 관문마다 전체 테스트 1, 리뷰어 재실행 0이다. 각 설정을 한 번씩만 돌렸으므로 편차는 확인하지 않았다.
