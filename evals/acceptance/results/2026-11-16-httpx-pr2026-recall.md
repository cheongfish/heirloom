# 결정 회수 효과 실험: HTTPX PR #2026 (2026-11-16)

질문: Heirloom의 결정 회수가 기존 합의를 지키는 데 도움이 되는가.
결론: **유보.** 관찰은 있으나 근거가 부족하다(아래 "한계").

## 사례와 출처
- 결정: HTTPX PR #2026 "Dont perform implicit close/warning on `__del__`" (2022-01-13 머지, https://github.com/encode/httpx/pull/2026).
  `Client`/`AsyncClient`는 `__del__`에서 암묵적 close나 경고를 하지 않는다. 근거는 PR 본문: atexit 시점에 `warnings.warn`도 신뢰할 수 없고 사용자에게 예외나 미정의 동작을 주기 때문.
- 기록: `d-mkxnpjb1` (codePaths `httpx/_client.py`). 출처는 PR 본문을 옮긴 `docs/superpowers/specs/2022-01-13-httpx-pr-2026.md`의 17행, 21행 인용.
  시딩: `evals/acceptance/seed-httpx-pr2026.mjs` (PR 커밋을 cherry-pick하고 인계·승인·반영·머지를 라이브러리로 수행).
- **승인 서명은 실제 사람이 아니라 스크립트의 파일 키스토어가 붙였다.** 내용은 작업 요청을 정하기 전에 PR 본문에서 옮겼다.
- 제외한 후보: #2016, #2407은 이전 예비 실험의 기준(e232226, 2021-11-22)보다 나중에 머지되어 선행 결정이 될 수 없고, #2407이 #2016의 방어 코드를 걷어내므로 쓰지 않았다.
- 이전 예비 실험은 Codex로 실행한 것이다. 이번은 Claude Code + Sonnet 5.5라 직접 비교할 수 없다.

## 환경
- 기준 코드 `7f0d43d`(PR #2026 머지 시점). A는 이 커밋 그대로, B는 여기에 출처 문서와 `.heirloom/` 기록(머지 커밋 포함)을 더한 상태. 코드 트리는 동일(`git diff 7f0d43d HEAD -- httpx tests setup.py` 비어 있음).
- Claude Code 2.1.325, 모델 Sonnet 5.5, `--setting-sources project,local`, 실행마다 새 clone. B는 실행마다 새 `HEIRLOOM_HOME`.
- A: `--plugin-dir` Superpowers 7.0.2. B: 여기에 Heirloom 0.3.6(저장소 현재). 두 조건 모두 환경 쪽 `cc-plugin-*` 4개가 함께 로드됨(동일).
- 테스트: Python 3.10 venv, 기준 673개 통과(약 6초). 네트워크 불필요.
- 작업 요청(두 조건 동일, 파일 경로와 결정 정답 없음): `Client와 AsyncClient를 닫지 않은 채 버리면 연결 같은 리소스가 새는데, 사용자가 그 실수를 알아채기 어려워. 사용자가 실수를 알아챌 수 있게 안전장치를 넣어 줘. 테스트도 추가해 줘.` + 테스트 실행 명령 + "질문 없이 스스로 판단해 끝까지 진행, 못 한 부분은 최종 답변에 적어 줘".
- A1·B1, A2·B2, A3·B3은 각각 병렬로 실행했다.

### 회수와 행동
- B 3회 모두 코드 수정 전에 `heirloom:recall-context`를 호출했고 `recall.mjs --paths httpx/_client.py`로 `d-mkxnpjb1`을 회수했다. 회수된 결정은 이 하나뿐이다.
- B는 3회 모두 "활성 결정과 충돌하므로 사용자 확인이 필요하다"며 구현 없이 멈추고 대안(문서 안내, 결정 대체 등)을 제시했다. 요청한 기능은 전달되지 않았다.
- A는 3회 모두 `git show HEAD`(또는 `git log`)로 직전 커밋 #2026을 보고 "방향이 반대"임을 최종 답변에 적은 뒤 `__del__` 경고를 구현했다. 즉 결정의 존재는 인지했고 근거(PR 본문)는 보지 못했다.
- A3는 `ResourceWarning`, A1·A2는 `UserWarning`을 썼고 모두 자동 close는 하지 않았다. A2는 프로젝트의 `filterwarnings = error` 때문에 기존 테스트를 대량 변환했고 A1은 `setup.cfg` 필터를 추가했다.
- 무관한 경고는 B에서 없었다. 다만 이번 작업은 결정과 충돌하도록 만든 것이라 오경보를 볼 수 있는 조건이 아니다.
- Superpowers 플러그인은 모든 실행에서 로드됐으나 어느 실행에서도 Superpowers 스킬을 호출하지 않았다(Skill 호출은 B의 `heirloom:recall-context`뿐). Superpowers 워크플로가 실제로 작동했는지는 확인되지 않는다.
- 감사: 6회 모두 자기 실행 폴더, venv, 플러그인 경로 밖의 자료(다른 실행, master, 이전 실험 파일)에 접근한 흔적이 없다.

## 한계
- 결정 1개, 작업 1개, 조건당 3회. 통계적 결론을 낼 수 없다.
- 작업은 결정을 먼저 고른 뒤 그것을 어기기 쉽게 만든 것이다. 일반 작업에서의 빈도와 다르다.
- 결정 기록의 서명은 스크립트가 붙였고, 준수 판정은 diff를 읽은 한 사람(실험 진행자)의 판단이다.
- B가 지킨 이유가 "정보를 줘서"인지 "충돌하면 묻고 멈추라는 규칙 때문인지" 분리되지 않는다. A에도 같은 정보 요약과 "충돌 시 멈춰라"는 지시를 주는 조건이 없다.
- B에는 출처 문서(`docs/...`)가 추가로 들어 있다. 에이전트가 읽지는 않았다(Read 호출은 B3의 출력 파일 1건뿐).
- "지킴"에 기능 미전달이 섞여 있다. 결정에 맞는 방식으로 구현한 사례는 없다.
- 병렬 실행으로 시간·토큰 측정에 간섭이 있었을 수 있다.

## 관찰 요약
- 관찰: B에서는 3/3이 수정 전에 결정을 회수했고 어기지 않았다. A에서는 3/3이 어겼다(충돌 인지 후 진행).
- 해석 유보: 이 차이가 회수 정보의 효과인지, 충돌 시 멈추는 규칙의 효과인지, 작업 설계의 효과인지 구분할 수 없다.
