# 결정 회수 효과 실험 4차: Heirloom 실제 규칙 문구만 준 조건 C′ (2026-11-17)

[3차 실험](2026-11-16-recall-vs-rule.md)에서는 B(Heirloom)와 C(규칙만)가 구분되지 않았다. 다만 C의 규칙 문장은 실험자가 쓴 것이었고, 결정을 찾을 곳(git 이력, 문서, 변경 기록)도 알려 줬다.
이번에는 조건 D(= C′)를 더했다. D는 Heirloom 스킬의 실제 규칙을 옮긴 문장만 주고, 결정을 찾을 곳은 알려 주지 않는다.
**결론: 유보. 다만 회수 쪽으로 약하게 기운다.** D는 결정을 15회 중 13회 지켰다(B·C는 15/15). 어긴 2회는 모두 결정 커밋을 찾아 읽고도 "이건 결정이 아니다"라고 판단한 경우다. 표본이 작아 B·C와 통계적으로 구분되지는 않는다.

## 조건
- **D (C′)**: C와 같은 환경이다(Superpowers만 쓰고 Heirloom 플러그인과 `.heirloom/` 기록은 없다). 프롬프트에는 작업, 다음 규칙, 테스트 명령, 3차와 같은 "질문 없이 끝까지" 문장을 넣었다.
  > 수정하기 전에 고칠 파일과 주제에 관련된 이 프로젝트의 결정과 원칙을 찾아 전문을 읽어 줘. 머지되어 현재 유효한 결정만 확정된 규칙이고, 대체·폐기되었거나 머지되지 않은 것은 규칙이 아니야. 결정을 따르거나 벗어날 때는 어떤 결정인지 밝혀 줘. 유효한 결정과 어긋나게 고쳐야 한다면 멈추고 사용자에게 물어봐. 관련 결정을 못 찾았다면 확인한 범위에서 없다는 뜻일 뿐이니, 어디를 확인했는지 밝히고 빠짐없이 확인했다고 말하지 마.
- 출처: `skills/recall-context/SKILL.md`의 "Apply and report" 절과 `skills/using-heirloom/SKILL.md`의 "Project context" 절이다. 3차 B 실행 때와 같은 버전이다(c87d4cc 압축본, 0.3.6).
  - 전문 읽기: "Read full records before relying on them."
  - 유효 판정: "Only `active` … records are confirmed rules."
  - 따르거나 벗어날 때 밝히기: "Cite ids when following or departing."
  - 충돌 처리: "To contradict an active record, stop and ask the user."
  - 확인 범위 공개: "Empty `records` means no match …, not that no decision exists" / "do not claim exhaustive coverage."
- 뺀 것: 기록 id, `pending`/`unknown` 상태, 인계(handoff)에서 대체안 제안하기. 모두 Heirloom 도구가 있어야 의미가 있다.
- B와 마찬가지로 "멈추고 물어봐"는 "질문 없이 끝까지"와 충돌한다. B의 실제 상황과 같게 두었다.
- 실행: `run-case.sh <case> D <n>`, 작업 5개 × 3회 = 15회. 모두 순차로 실행했고 각 실행은 900초·$6 제한이다. 모델은 Sonnet 5.5, Claude Code는 2.1.326이다(3차는 2.1.325). 작업, 기준 커밋, 검증은 3차와 같다.

## 해석
- **관찰**: Heirloom의 규칙 문구만 줘도(D) 어김은 크게 줄었다(A 12/15 → D 2/15). 규칙의 효과는 크다.
- **D는 B·C보다 약간 약하다.** B와 C는 0/15, D는 2/15다. 그러나 Fisher 정확 검정(양측)으로 p≈0.48이라 구분할 수 없는 수준이다.
- **어긴 원인이 회수가 메우는 틈과 맞닿아 있다.** D는 결정을 찾는 데는 실패하지 않았다(15/15가 해당 커밋에 도달). 실패한 곳은 "이 커밋이 확정된 결정인가"를 스스로 판정하는 단계였다. Heirloom 기록은 이 판정을 `status: active`로 대신 내려 준다. B는 같은 두 작업에서 6/6 지켰다.
- **C가 B와 비슷했던 이유 가설**: C의 문장은 "git 이력, 문서, 변경 기록에서 이미 합의된 결정이 있는지 확인"하라고 했다. 이 문장이 커밋 기록 자체를 결정으로 보도록 이끌었을 수 있다. D는 "결정과 원칙"을 문서로 먼저 찾았고, 문서가 없자 커밋을 결정으로 볼지 재량으로 판단했다. 이 가설은 이 자료로 검증하지 않았다.
- 따라서 "회수는 규칙에 더하는 가치가 없다"는 3차의 잠정 결론은 C의 문구 덕일 수 있다. 회수의 가치는 결정을 **찾는 것**보다 **확정된 결정이라고 못박는 것**에 있을 가능성이 있다. 아직은 가설이다.

## 한계
- 독립 표본은 작업 5개뿐이다. 차이는 2회이고 그 2회도 서로 다른 작업에서 1회씩 나왔다. 같은 조건을 다시 돌리면 0이나 4가 나올 수 있다.
- A·B·C는 어제(2026-11-16), D는 오늘 실행했다. Claude Code 버전도 2.1.325에서 2.1.326으로 바뀌었다. 모델과 플러그인 구성(superpowers + 사용자 공통 플러그인 4개)은 같다.
- D와 C는 두 가지가 다르다. 하나는 찾을 곳 안내의 유무, 다른 하나는 충돌 시 행동 지시("지키는 범위까지만 진행" vs "멈추고 물어봐")다. 이번 설계로는 둘을 분리할 수 없다.
- D의 규칙은 내가 영어 스킬 문구를 한국어로 옮긴 것이다. 의미는 맞췄지만 B에 주입되는 원문(영어, 스킬 전체 맥락 포함)과 같은 자극은 아니다.
- 준수 판정은 결정 검사 스크립트와 내가 diff·답변을 읽은 판단이다. 독립 채점자는 없다.
- 사용자 전역 설정의 일부(CLAUDE.md 등)가 에이전트 맥락에 들어간 흔적이 있다(web1-D2가 `rules/pstack-models.md`를 언급함). 모든 조건에 공통이라 비교에는 영향이 없다고 보지만 확인하지는 않았다.
- 하네스 결함(3차부터 있었음): data1의 `test_cmd`가 환경 변수 접두사로 시작해서 `run-case.sh` 후처리의 `timeout 300 $TEST_CMD`가 실행되지 않는다. D의 data1 3회는 코드 변경이 없었고, 사후에 직접 돌려 1097개 통과를 확인했다.
- 환경: Linux(WSL2), 네트워크 없이 테스트. 실행 결과는 `~/heirloom-acceptance/cases-runs/*-D{1,2,3}/`.
